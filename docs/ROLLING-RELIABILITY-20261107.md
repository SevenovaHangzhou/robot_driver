# Rolling 持续点动可靠性与第 3、4 项部署

本轮对应用户“按序进行优化，部署34”：先处理接收侧瞬态快照读取，再处理 Mink 动态边界，最后联合部署时延分布和拒绝详情。日志分析见 `ROLLING-LOG-ANALYSIS-20261107.md`。部署前不等同于真机运动验证通过。

## Rolling 接收侧

`readRtStateView()` 仅由非实时接收、查询回调调用。遇到正在写入的版本或前后版本变化时，间隔 50 μs 重读，最多 64 次，时间预算取已配置的 `maximum_controller_period_ns`（当前真机为 2 ms）。正常一次读到快照时不等待；操作系统调度可能使实际唤醒晚于预算。实时 update() 不增加等待、锁、日志或分配。

读取成功仍要求完整一致的版本、有效指令、运行状态及 epoch；轨迹 prepare 后、commit 前仍重读当前边界。持续忙碌时保守拒绝，不使用上次缓存冒充新快照，不自动重发或继续运动。公共消息和结果码不变。

非实时拒绝主题增加 reason：snapshot_busy、state_not_running、epoch_changed、invalid_desired、time_overflow、snapshot_publish_failed、feedback_stale、takeover_mismatch、sequence_overflow。操作台仅转发与当前 epoch/sequence/result 匹配且未过期的详情。

## Mink 动态边界

模型及 artifact 的位置、速度、加速度、跟随误差、碰撞和制动包络均保持原值。客户端 QP 使用原速度、加速度上限的 98% 作为规划预算，留出跨语言三次曲线求值和求解残差的空间。

段内加速度线性变化，三次位置的速度是二次 Bézier 曲线，控制点为 `v0`、`v0 + a0*T/2`、`v1`。QP 同时约束本段末速度 `v1` 和下一段的控制点 `v1 + a1*T/2`；从静止锚点开始，逐段保证整个速度控制多边形处于预算内，也为松手后先将加速度降到零预留条件。

松手尾段先用一个原有采样周期将残余加速度连续降到零，再生成连续制动尾段。位置、速度、加速度接缝保持连续，最后速度/加速度归零。整个窗口仍执行精确插值动态检查及双臂、自碰撞检查，不截断单轴、不跳过校验。真实位置边界或碰撞不可行时仍会停车。

18121 首段加速度拒绝记录完整 17 位有效数字及超出量，避免再次显示两个相同的四舍五入值。

## 第 3、4 项

18131 显示输入、规划、发布、ACK 等耗时的 P50/P95/P99/最大值，以及最近一次退出原因。控制器对拒绝窗口发布关节、段号、时间、量值和限值；读取失败显示实际分支，缺少证据时不推测关节。

部署继续使用初窗 120 ms、替换窗 100 ms 的基线前瞻，不自动切换到较低前瞻。两端仍共用 18121 的互斥控制权。并行加入的 J7 姿态控制保留。

## 离线验证

- Rolling：8 个 C++ 套件、63 项通过，包括短暂快照忙后恢复、持续忙时有界拒绝、1 kHz update 与持续窗口替换并发、生命周期和实时路径分配检查。
- 客户端：406 项通过、180 项因已有环境/旧链路条件跳过；旧 ROS 测试 `test_rolling_ros.py` 依赖当前公共接口已移除的 OpenRollingJointSession，未纳入本轮。实际生产链路使用当前 RollingJointTargetBatch 与官方 RollingSender。
- 操作台：372 项通过，包含官方发送绑定的本机 ROS 传输；全部最终回归使用与真机隔离的本机 Domain 219。
- 前端输入、登录恢复脚本检查通过。
- 新增独立 CubicHermiteSpline 检查：动态边界随机迭代、正反向高速制动、左右臂三个平移方向的实际 Mink QP 输出。

本轮不主动发送真机使能或运动命令。安装需要控制权空闲，并有序重启控制栈以加载插件；重启后的现场运动由操作者执行。部署结果单独记录在相邻 `.runtime/rolling-reliability-20261107/`，以实际回执为准。
