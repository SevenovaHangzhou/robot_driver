## Rolling 侧应优先检查的路径

远端实际源码 rolling_trajectory_state.cpp 的 SHA256 为 35e1ec889d6726adea748f5298f73c0c51dfd0411170f0cba49a71b4424291a6，与离线实验使用的同一文件一致。

1. 实时 update() 全程使用 RtStateVersionGuard；更新开始将版本变为奇数，结束恢复偶数。
2. 非实时 readRtStateView() 立即尝试最多 8 次；看到奇数就继续，没有等待一个完整实时写周期。
3. buildAdmissionContext() 将“暂时未读到一致快照”与“真实不运行/状态无效”等情况统一返回 false。
4. admitBatch() 在 prepare 前、commit 前各调用一次，任一次 false 就返回 NOT_ACCEPTING=9。
5. 18131 收到该拒绝后退出当前运动，并发出软件停车。随后页面显示的“保活失败：键盘接管已失效”通常晚于规划退出，是退出后的表现，不能倒置为根因。

离线构造“会话始终 RUNNING、实时写入版本为奇数”的状态，调用实际编译的读取/接收上下文函数：写入前成功，写入期间两个函数失败，写入后恢复成功，会话状态未改变（见 jog-offline-snapshot-result.json）。这验证了故障路径存在；没有在真机回调中采集分支计数，因此尚不能逐条证明 4 次码 9 全部由此产生。

建议在非实时侧采用有明确时限的读取重试，或提供已完成且带版本/时间的新鲜快照。真实 STOPPING、epoch 改变、过期及无效数据仍必须拒绝；提交前必须重新确认边界。实时 update 不等待非实时锁。诊断应细分 snapshot_busy、state_not_running、epoch_changed、invalid_desired、snapshot_publish_failed 等接收失败原因。

## 客户端也有两类可复现的边界问题

### 加速度贴上限

Mink 的端点加速度允许达到 artifact 上限 1.0471975511965976 rad/s²。客户端窗口校验使用 2e-7 加速度数值容差，18121 首窗与 Rolling 控制器则严格比较上限，而且 Python 与 C++ 的三次曲线系数求值顺序不同。

离线用相同 20 ms 间隔、相同积分与首段公式，在 q0=2 rad、a0=0、a1 恰等于上限时，重建加速度比上限多约 2.73e-12 rad/s²；q0=1 rad 时还可出现 Python 首段通过、C++ 曲线重建略超上限。该实验说明贴限规划会放大数值差异；没有原始失败点和未格式化 peak，不能认定真机 5 次均只超出上述幅度，也不能排除 QP 残差。

建议规划时向内保留经过离线验证的加速度/速度预算，并统一客户端与控制器的插值计算。优先从规划侧减少贴限，保留硬件安全包络；补充完整精度的 value/limit/excess。

### 只约束端点速度无法保证段内速度

real_source.py 的 QP 约束端点加速度和下一点速度，validate_window() 则检查整段三次曲线的速度极值。它们覆盖范围不同。

离线反例：T=20 ms，速度上限 0.5235987755982988 rad/s，v0=v1=0.5225987755982988 rad/s，a0=+1.0471975511965976、a1=-1.0471975511965976 rad/s²。端点速度与加速度满足限制，但段中速度达到 0.5278347633542818 rad/s，超限约 0.004236 rad/s。

建议将段内速度峰值/可制动性纳入规划，或对失败候选执行有界减速与重新规划，随后对整段重新进行动态和碰撞检查。不能只缩放点速度、截断单个关节或略过校验，否则会破坏 q/v/a 接缝。两条 rolling_dynamics 日志尚未细分位置和速度，反例验证算法缺口，不等同于已重建那两次故障。
