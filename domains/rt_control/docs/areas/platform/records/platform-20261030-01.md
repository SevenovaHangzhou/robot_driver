## 背景

用户本轮要求修复启动，不执行之前已取消的 temp 融合任务。原失败日志为 runs/chassis-20261030T044302Z/launch.log。
现场 can0 的 USB 序列号是 BMS 的 004D00675230500720333159；底盘编码器及IMU的已登记适配器 003000265230500720333159 被枚举成 can1。
底盘预检按 deployment.yaml 中的真实身份拒绝启动，属于正确保护；不得把部署序列号修改为当前错误占位设备。
任务范围为宿主启动前接口绑定、启动包装器和回归，不改控制器、模型、模式切换、总线协议或安全阈值。
验收条件：纠正接口映射、未知身份拒绝、运行中禁止重命名、chassis start 到达硬件活动未使能状态。

## 改动

- 新增 hostsetup/rt-control-chassis-can-bind.py。按上述已有登记序列号生成完整重命名计划，先检查底盘适配器存在、保留名未知设备、序列号重复和临时名冲突，再检查 controller_manager 未运行。
- 对调时先将受影响接口关闭并改成临时名，再绑定 can0/can1，防止占名冲突；命令失败立即停止，不自动启动业务或使能。已正确的接口保持原状。
- 以 root:root 0755 安装为 /usr/local/sbin/rt-control-chassis-can-bind。现场 v3-restart.sh 在配置 can0 的500kbit/s之前调用该工具，原始脚本保留于本任务证据备份。源码脚本位于版本化 hostsetup，非引入新的启动服务。
- 被挪动的非底盘总线保持 DOWN，由其原有功能启动入口设置波特率并启用；本次不启动BMS。保留 rt-control-can-names.service 与 can1.service 不在开机启用的已有裁决。
- 启动预检继续检查USB身份；导航CSV、作业CSP及既有换向修复不变。

## 验证

- python3 tools/tests/test_chassis_can_bind.py：6项通过，覆盖无需修改、双适配器交换、单底盘适配器、未知/缺失/重复身份/临时名占用、运行中/进程检测失败拒绝、ip失败停止后续操作。

- 实机先按序列号纠正接口映射，再通过原 chassis.sh start 入口启动。启动证据见上列归档；不发使能、复位或运动命令。
- --check 为只读检查，可在运行中验证映射，正确时不重配总线。

本记录不授权使能或运动。

## 结论与冻结事实

- F1: 本机底盘 can0 必须对应 003000265230500720333159，BMS can1 对应 004D00675230500720333159，不能以USB枚举先后替代身份。
- F2: chassis start 显式启动流程在底盘波特率设置前纠正绑定；不新增开机启动服务，不关闭USB身份预检。
